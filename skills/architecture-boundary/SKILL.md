# 架构边界与分层架构图

在跨模块或新架构方案动代码前，先用一张**职责与通信边界图**把隐蔽耦合、伪需求和跨层依赖晒在台面上，再进入实现。

## 好的架构图必须回答 5 个问题

1. **主轴一句话**：顶部先用一句话说清核心分层原则（谁是薄宿主/基础设施，谁承担业务变化）。
2. **职责归属与“不做什么”**：每个框不仅写清负责什么，更要写清**显式禁止边界**（不拥有什么状态、不引入什么分支、不另建第二套逻辑）。
3. **状态真相唯一归属**：每类核心状态/数据只归一个 owner，标注“事实归属”与“只读投影/转发”，禁止跨层复制或从上游日志/文案反推业务状态。
4. **区分职责模块与合同/边界**：明确哪些是业务模块、哪些是中立合同/端口、哪些是装配入口；图中区域表示**职责边界**，不等同于必须新建进程、服务或目录。
5. **箭头带语义与方向**：每条连线标明传递什么（输入/控制、只读查询、写回、装配、事件），禁止含义不明的双向裸箭头。

## 动代码前必附的核对项

- **需求 vs 假设**：把用户明确需求与原型/AI 自行补全的设想分开列；未确认设想不得成为架构硬约束（尤其是会引入跨模块聚合、新持久化或状态机泄漏的假设）。
- **变化归属**：正常业务变化落在哪一层，什么情况下才允许改底层/公共层。
- **不替现网代码辩护**：评审或被质疑时，从目标与边界重新判断，不把既有实现惯性当合理性依据。
